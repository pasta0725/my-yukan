Changelog
エージェントの登場でコードを書くコストは下がりましたが、ユーザーが作るアプリやツールのほとんどは、いまだに localhost の外に出ることがありません。
これからは、Cursor 上でライブアプリを直接構築し、リンクで共有できます。作りたいものを説明するだけで、アプリの構築からデータベースのセットアップ、認証の設定、デプロイまで、あとはすべて Cursor が引き受けます。
今回のリリースにより、組織内の誰もが自分の業務に役立つツールを構築し、チームメンバーと共有できるようになりました。Cursor を更新して、ぜひお試しください。
#
仕組み
はじめるには、
クラウドエージェント
を起動し、アプリを構築したいと明示的に伝えます。
Cursor はウェブアプリの雛形を作成し、必要に応じて Postgres データベースを立ち上げ、Cursor SSO による認証を設定し、ホスティング環境を用意します。データウェアハウスなど、既存のシステムにアプリを接続する必要がある場合は、Cursor が必要なシークレットの入力を求めます。
アプリを公開する際は、一意のドメインを選ぶだけで、Cursor がすぐにアクセスできる公開リンクを発行します。
Cursor 社内では、営業、オペレーション、法務、財務、エンジニアリングなど、さまざまな部門のユーザーが社内アプリを構築しています。特に役に立っているものの例は次のとおりです。
イベント登録、アカウントの割り当て、座席管理などの社内業務ツール
スライド、動画、インタラクティブなデモを組み合わせたお客様向けのマルチメディアプレゼンテーション
新入社員向けの学習、イネーブルメント、オンボーディング用コンテンツ
営業チームがパイプラインや商談機会を把握するためのリアルタイムダッシュボードやツール
エンジニアリングサービスを管理するためのポータル
Cursor は、Cursor Origin と GitHub 上の新規または既存のリポジトリからアプリをデプロイできます。GitLab など他の Git プロバイダーのサポートも近日公開予定です。
#
コントロールとガードレール
アプリを公開する際、Cursor は決定論的なチェックとエージェント型のセキュリティチェックを実行し、アプリのファイルに書き込まれたシークレットや露出した認証情報など、よくある Issue を検出します。チェックに失敗した場合は、何を修正すべきかをエージェントが知らせます。チェックに合格し、明示的に公開操作を行うまで、アプリが公開されることはありません。
チーム管理者は、チーム内のすべてのアプリとシークレットを確認できます。さらに、セキュリティレビューに独自のルールを追加したり、レビューでブロックされた公開を承認したり、任意のアプリを非公開にしたりすることもできます。
#
チームと共有する
チェックに合格すると、Cursor は指定した URL にアプリをデプロイします。その後、特定のユーザー、グループ、またはチーム全体とアプリを共有できます。いずれの場合も、アクセスには Cursor へのサインインが必要です。個人向けプランでは、アプリを一般公開することもできます。
スクリプトや Grok Bot からアプリを使いたい場合は、Cursor APIキーを発行することもできます。

Cursor の発表
は背景をこう説明している。エージェントでコードを書く費用は下がった。それでも、利用者が作るアプリや道具の多くは localhost から外に出ない。localhost とは作った人の PC の中だけで動いている状態を指す。
新しい機能では、作りたいものを文章で伝えると Cursor がアプリを作る。必要ならデータベースを用意し、認証（ログインの仕組み）を設定し、公開まで進める。
始めるには、クラウドエージェントを起動し、アプリを作りたいとはっきり伝える。クラウドエージェントは Cursor のサーバーの上で作業を進める AI のことだ。
Cursor の説明書によると、この機能は PC の中で動かすエージェントでは使えない

アプリを作るとき、Cursor は4つの作業を受け持つ。Web アプリのひな形を作り、必要なら Postgres というデータベースを用意する。認証は Cursor SSO で設定する。SSO は1つのアカウントで複数のサービスにログインする仕組みだ。アプリを置いて動かす場所（ホスティング）も用意する。
データウェアハウス（社内のデータを集めた保管庫）など、社内の仕組みにつなぐこともできる。そのときは、Cursor が必要な秘密の情報（パスワードや鍵）を尋ねる。公開するときは、ほかと重ならないドメインを選ぶ。Cursor はそのアドレスで動くリンクを返す。
アプリは新しいリポジトリからも既存のリポジトリからも公開できる。リポジトリはコードの保管場所で、対応するのは Cursor Origin と GitHub だ。Cursor Origin は Cursor が運用する Git ホスティングである。
Cursor の社内で作られた例として、発表はイベントの受付や座席の割り当ての道具、新入社員の研修、営業が案件を把握するダッシュボードなどを挙げる。
公開の前には、決まった規則による検査と AI による検査が行われる。説明書は毎回必ず動く検査を4つ挙げる。ファイルの中の API キーやアクセストークン、秘密鍵などを含むファイル、.env ファイル、ソースマップ（元のソースコードを読めるようにするファイル）を、公開から外すか公開を止める。
検査に通り、利用者がはっきり公開を選ぶまで、アプリは公開されない
。
チームの管理者はチームのすべてのアプリと秘密の情報を見られる。検査に独自の規則を足すこと、検査が止めた公開を承認すること、どのアプリの公開もやめることもできる。

【用語解説】
Cursor のライブアプリ公開機能とは
この記事のポイント
Cursor は 2026 年 11 月 5 日、Cursor 内で構築した Web アプリをリンクで共有できる機能を発表しました(2026年11月時点)。
必要に応じて Postgres データベース、Cursor SSO による認証、ホスティングを Cursor が用意します。
クラウドエージェントが有効なすべての有料プランで利用でき、セキュリティチェック通過と利用者の明示的な公開操作が公開の条件です(2026年11月時点)。
Cursor でコードを書き、できた Web アプリを同僚に見せるためにデータベースやホスティングを別途手配していた開発者は、その手配を Cursor に任せられるようになりました。Cursor が 11 月 5 日に発表したライブアプリ公開機能です。公式リリースノートによると、Cursor は Web アプリの雛形を作り、必要な場合に Postgres データベースを起動し、Cursor SSO の背後に認証を設定し、ホスティングを用意します。
対象は、クラウドエージェント(Cursor のクラウド側で動くエージェント機能)が有効なすべての有料プランです(2026年11月時点)。無料プランでの利用についてはリリースノートに記載がありません。
仕様の要点と公開までの流れ
要点は、Cursor がインフラの用意と公開前チェックまでを引き受け、公開のボタンだけは利用者が押す、という分担です。
Cursor が用意するものは次の 4 つです。
Web アプリの雛形作成
必要な場合の Postgres データベース起動
Cursor SSO による認証設定
ホスティング
公開前には、Cursor が決定論的なチェックとエージェントによるセキュリティチェックを実行し、よくある問題を検出するとしています。決定論的なチェックは規則ベースで毎回同じ結果を返す検査、エージェントによるチェックは AI エージェントがコードを読んで判断する検査です。そして、チェックを通過し、利用者が明示的に公開するまでアプリは公開されないと明記されています。
デプロイ先について、公式ドキュメントは、各アプリをチーム用、または個人プランの場合は利用者用に Cursor が作成する専用アカウントへデプロイすると説明しています。自分の既存クラウドアカウントに置くのではなく、Cursor が作る分離されたアカウントに載る点は、評価時に押さえておきたい仕様です。
社内システムとの接続については、Cursor は、アプリがデータウェアハウスなどの自社システムに接続する必要がある場合、必要なシークレットの入力を求めると説明しています。
どの開発者に、何が起きるか
いちばん影響を受けるのは、社内の誰かに「ちょっと見られる画面」を作って渡す場面を抱えている開発者です。
たとえば、データウェアハウスの集計結果を一覧で見せる簡単な社内向け画面を作る場面を考えます。これまでは、画面のコードを書いたあとに、置き場所の確保、社内メンバーだけが見られるようにする認証、場合によっては一時的な保存先のデータベースを、それぞれ別に用意する必要がありました。今回の機能では、その 3 つを Cursor 側が用意し、認証は Cursor SSO に寄せられます。データウェアハウスへの接続に必要な接続情報は、Cursor が求めるシークレットとして渡す形になると Cursor は説明しています。
一方で、技術者が評価の前に確認しておくべき制約が 3 つあります。
公開範囲の既定
: 公式ドキュメントによると、Teams と Enterprise では一般公開の共有が既定で無効です。チームで試す場合、リンクを渡しただけでは社外の人は見られない前提で設計を考える必要があります。
Git プロバイダー
: リリースノートは、GitLab など他の Git プロバイダーへの対応を「coming soon」としています(2026年11月時点)。GitLab を使うチームは、現時点ではこの機能の評価を待つことになります。
デプロイ先の分離
: 専用アカウントへのデプロイという設計のため、既存のクラウド環境と同じネットワークや権限の中に置きたい用途には、そのまま当てはまらない可能性があります。この点を自社の要件に照らして確かめるのが、評価の最初の一歩です。
次にできることとして、クラウドエージェントが有効な有料プランを使っているなら、社内向けの小さな画面を 1 本だけ試して、公開前チェックの内容と専用アカウントの扱いを自分の環境で確かめるのが現実的です。社外に見せる用途を想定している Teams / Enterprise 利用者は、一般公開の既定が無効である点を先に確認してください。
編集部の見方
編集部は、この機能の本命は社外向けのサービス公開ではなく、
社内向けの小さなツールを素早く配ること
にあると見ています。
根拠 1: 認証を Cursor SSO に寄せ、Teams / Enterprise では一般公開の共有を既定で無効にしている設計は、社内メンバーの間で回す用途を前提にしています(2026年11月時点)。
根拠 2: 専用アカウントへのデプロイと、チェック通過かつ明示的な公開操作という二重の安全弁は、「うっかり外に出る」事故を抑える方向に効いています。社内の集計画面やダッシュボードのように、作ってすぐ渡したいものほど、この安全弁の価値が大きくなります。
根拠 3: GitLab など他の Git プロバイダーへの対応が「coming soon」の段階なので、全社の標準基盤として据えるにはまだ条件がそろっていません。
この見方が変わる条件は、公開範囲の設定が柔軟になり、他の Git プロバイダー対応が公式に提供された時点です。そうなれば、社外の関係者に見せるプロトタイプ共有まで、同じ流れで扱える道具に変わります。それまでは、社内向けの軽い用途から評価を始めるのが、今回の仕様から読み取れる無理のない使い所です。
