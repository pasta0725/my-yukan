GitLab released Community Edition and Enterprise Edition 19.6.1, 19.5.8 and 19.4.10 on November 20, 2026, as a critical security patch for self-managed installations. The 
GitLab release notice
 says the builds replace a vulnerable bundled Ruby runtime and address CVE-2026-132825, a heap buffer overflow in string case conversion. GitLab recommends that affected self-managed installations upgrade immediately. GitLab.com and GitLab Dedicated already run patched versions, according to the company.
The patch has an important deployment distinction. Official GitLab Linux packages and container images include patched Ruby. A self-compiled GitLab installation must also rebuild the Ruby installation that runs GitLab, using Ruby 3.3.14 or 3.4.13 or a later release in the same minor series. Updating GitLab application files while leaving a vulnerable self-compiled Ruby interpreter in place would miss the runtime change the vendor calls out.
Which GitLab versions are affected?
GitLab lists the affected CE/EE ranges as all versions before 19.4.10, 19.5 releases before 19.5.8, and 19.6 releases before 19.6.1. The three November 20 builds are fixes on three separate release lines, not one combined version. An inventory should record the complete installed GitLab version, its release line, and its deployment method before selecting an update.
For an installation on the 19.6 line, the named fixed patch is 19.6.1. For 19.5, it is 19.5.8; for 19.4, it is 19.4.10. A deployment older than those lines is within the affected range in the GitLab notice and needs a supported upgrade route. The wording does not establish that every affected instance is reachable by a remote attacker. It establishes that the vulnerable runtime is in those product versions and that GitLab has issued fixed builds.
The patch follows the 
November 16 GitLab security update
. The version numbers should stay distinct in change records: 19.5.6, 19.4.8 and 19.3.9 addressed a different set of issues. The November 20 release is a new critical patch across the 19.6, 19.5 and 19.4 lines. A system updated to a November 16 build may still require the newer Ruby fix.
What CVE-2026-132825 does
The 
Ruby security advisory
 describes a one-byte heap buffer overflow during case conversion of strings in some single-byte encodings, including ISO-8859-1 and Windows-1252. Case conversion changes letter case, such as upper to lower, while processing a string. In the vulnerable path, Ruby can write one byte past the end of the output buffer. The advisory says proof-of-concept cases demonstrate remote code execution in some scenarios. It does not say that every use of case conversion is exploitable.
GitLab says that, under certain conditions in GitLab, changing the case of a crafted string can produce an out-of-bounds heap write. GitLab assigns the release’s critical label using the Ruby security team’s severity rating; the GitLab notice separately says MITRE rates the CVE High with a 7.4 CVSS score. Those labels describe the same upstream defect from different assessments. They do not prove exploitation in a particular installation or establish an incident without system evidence.
The upstream Ruby advisory lists fixed Ruby versions 3.3.14, 3.4.13 and 4.0.10. GitLab’s self-compiled instructions name the two Ruby minor series relevant to its supported build paths, 3.3 and 3.4. That difference is not a contradiction: the upstream project describes the language runtime broadly, while GitLab specifies the runtimes used to build its product. Self-compiled operators should follow GitLab’s build instructions for the deployed GitLab release rather than substitute an upstream Ruby version solely because it appears on the Ruby advisory.
Packaged and self-compiled installations need different checks
With GitLab’s official Linux package or container image, the November 20 patch includes the updated bundled Ruby. The useful verification is the running GitLab product version and the installed package or image version after deployment. In a self-compiled installation, the Ruby runtime is a separate part of the build. GitLab explicitly requires rebuilding it with Ruby 3.3.14 or 3.4.13, or a later release in the same minor series, to address CVE-2026-132825 and the other issues in the upstream Ruby advisory. Merely seeing GitLab 19.6.1 in an application checkout is not enough evidence that its interpreter was rebuilt.
GitLab Dedicated has a separate history. The vendor says it previously used internal-only 19.5.7 and 19.4.9 releases with interim mitigations, and that the November 20 public builds include all fixes from those internal releases. Those internal numbers are not customer patch targets for ordinary self-managed installations. GitLab.com and Dedicated customers do not need to take action for this patch, according to the release notice.
GitLab says these patches have no new database migrations and that multi-node deployments should not require downtime. It also notes that an Omnibus package upgrade normally stops services, runs migrations and starts them again by default, regardless of patch size. The two statements describe different parts of the upgrade process: the release carries no new migration, while the package’s standard service cycle still runs unless its behavior is changed under documented upgrade procedures. Change windows should follow the actual deployment topology and GitLab’s upgrade guidance, not a blanket claim of zero interruption.
What to verify after applying the patch
First, distinguish CE/EE self-managed systems from GitLab.com and Dedicated. For each self-managed instance, record the full version and whether it came from an official package, a container image, or a self-compiled build. Select 19.6.1, 19.5.8 or 19.4.10 as appropriate for the release line, or follow a supported upgrade path from an older version. A version string alone should not obscure an installation assembled from separately maintained components.
After the update, confirm that the running service reports the intended GitLab release and, for self-compiled installations, that the Ruby interpreter used by GitLab is the rebuilt fixed version. Check routine service health, repository access, CI/CD jobs and integrations that matter to the installation under its normal change procedure. Those functional checks are ordinary upgrade verification; they do not determine whether the vulnerability was ever exploited. Where compromise is suspected, preserve relevant evidence and use the applicable incident process rather than treating a successful patch as a historical clean bill of health.
The vendor states no fixed calendar deadline for all customers in the release notice. Its instruction is to upgrade affected self-managed installations as soon as possible. That recommendation reflects the critical patch and the upstream Ruby team’s demonstrated code-execution scenarios. The exact product version, deployment method and runtime build determine the concrete remediation path.

自社運用は使っている系列から更新先を決める
GitLabが告知に記載した対象は、19.4.10未満、19.5系列の19.5.8未満、19.6系列の19.6.1未満です。19.4系列は19.4.10、19.5系列は19.5.8、19.6系列は19.6.1が今回の修正を含む最初の公開版です。この表記は各系列の修正到達点です。たとえば19.5.7は数値上19.4.10より大きくても、19.5系列の自社運用で指定された更新先には達していません。Dedicated向けの中間緩和版の説明を、手元の自社運用パッケージに流用しないでください。

公式の緊急告知は今回の複数ノード配備では停止が不要と見込む一方、Omnibusパッケージの既定の更新ではサービスを停止し、移行処理を行って再起動すると説明しています。停止できる時間帯を決める際は、リリースノートの一文だけを根拠にせず、自社の配備方式で採用している公式手順と照合します。単一ノードで停止する構成と複数ノードで切り替えられる構成では、利用者に案内する時間や作業順も異なります。
スポンサーリンク
公式配布物は配備先まで追う
公式Linuxパッケージを使う場合は、修正を含むGitLabパッケージに更新します。ホストで普段使うRubyの更新だけを実行しても、GitLabパッケージ内の
ランタイム

公式コンテナでは、レジストリに新しいイメージがあることと、本番のコンテナがそのイメージで入れ替わったことを分けて確認します。取得したタグとダイジェストを配備記録に残し、稼働中のレプリカが意図した成果物を使っているかを点検します。旧レプリカを残したままロールアウトが止まっている場合は、更新が終わった扱いにしません。待機系や復旧用に保存したマニフェストも棚卸しし、切り替えや再配備で意図せず旧版に戻る経路を把握してください。
Helmで導入している場合も、チャートの版とGitLab本体の版を分けます。GitLab公式の経路ガイドからチャートと本体の対応表を参照し、利用中のチャートでどのイメージが使われるかを確認してください。運用側が個別にイメージを指定している場合、チャートを更新しても、その指定が古いイメージを指し続けることがあります。運用上の確認として、設定した版と現在動いているワークロードのイメージを突き合わせると判断しやすくなります。
自前ビルドは実行中のRubyを確認する
ソースから構築したGitLabでは、GitLab側のパッチだけではRubyを入れ替えられません。GitLabは、自社ビルドで使っているRubyを3.3.14または3.4.13、もしくは現行の同じマイナー系列の後続版で再構築するよう案内しています。Ruby単体には4.0.10の修正もありますが、それを根拠にGitLabの実行環境を4.0系へ切り替えてよいとは判断できません。今回の更新ではGitLabが案内する系列の範囲で対応します。
点検の出発点は、サービス定義、コンテナのビルド定義、起動ログにある実行環境です。運用端末で確認したRubyのバージョンをそのまま記録するのではなく、サービスを起動するユーザーやコンテナの環境と照合します。一つのホストに複数のRubyがある場合や、ビルド環境と実行環境を分けている場合、この確認が特に重要です。ビルド時に新しいRubyが確認できていても、最終イメージへ古いランタイムをコピーしていれば、本番では修正を使えません。
更新後は、Web処理だけでなく、別イメージや別ノードで動くバックグラウンド処理にも同じ確認を行います。新しい成果物を取り込んだ後、稼働中のサービスが更新後の環境で起動しているかを見てください。プロセス起動日やイメージ識別子を確認しておけば、ディスク上のファイルだけが置き換わった状態や、一部のノードに配備が届かなかった状態を区別できます。
自前ビルドの検証では、既存の正常系リクエストとジョブを使います。同じRuby系列内でも、再ビルドに伴ってネイティブ拡張の読み込み、依存ライブラリの解決、バックグラウンド処理の起動に差が出る可能性があります。

スポンサーリンク
更新完了の証拠と異常調査を分ける
運用上の完了条件は、①対象のインスタンスを特定した、②今回の修正を含むGitLab本体を配備した、③自前ビルドなら修正済みRubyで動作している、④通常の利用経路を確認した、の四つです。たとえばログインとプロジェクト表示は正常なのにキューだけ止まる場合、セキュリティパッチの適用と業務復旧の判定を分けて扱います。
CI
を利用するチームでは、テスト用ジョブの投入から結果反映までを見ておくと、更新作業の終了と利用再開を区別できます。
また、パッチが入ったことは、過去に異常が起きなかったことの証明にはなりません。更新前に異常なプロセス終了や説明できない設定変更が見つかっているなら、時刻、該当ノード、リクエストログ、プロセス再起動の記録を保持してください。単発のエラーをこのCVEの悪用と決めつけず、通常の障害、更新に伴う再起動、その他の侵害兆候との関係を調べます。一般的な運用上の提案であり、GitLabがこのCVEに固有の検知条件として公表したものではありません。
すぐ更新できない場合は、変更担当者と次に更新できる時間を特定し、外部から到達可能な環境を優先して扱います。アクセス制限を一時的に強めるなら、管理者用画面だけでなく、通常利用者や連携元の業務にも影響するため、残す経路を確認して実施してください。これで脆弱性の修正が完了するわけではありません。誤って旧版に戻した場合も同様で、業務を復旧できたかと、脆弱な構成へ戻ったかを別に判断し、再更新の条件を記録します。
今回の更新で確認すべきなのは、手元に修正ファイルがあるかではなく、どの配布物とランタイムが実際に処理を担っているかです。公式配布物なら修正済みの製品パッチを配備する経路を、自前ビルドなら本体とRubyをそれぞれ更新する経路を選びます。両者を同じ完了票で扱う場合でも、Rubyの確認欄には「公式同梱」と「自前で再構築」のどちらで修正を受け取ったかを残しておくと、次の緊急更新で対象をすぐに判断できます。

11月20日の修正：Rubyの脆弱性
GitLabの発表によると、CVE-2026-132825は、Rubyで
文字列の大文字・小文字を変換するときに、メモリの範囲外に書き込んでしまう
問題です。細工した文字列を変換させると、条件によってはメモリが壊れます。Rubyの開発チームは、場合によっては
外からプログラムを動かされる（リモートコード実行）
おそれがあるとしています。
深刻度は、Rubyの開発チームの評価がCritical、MITRE（CVE番号を管理する団体）の評価がHigh（CVSS 7.4）です。GitLabはRubyの評価にならってCriticalとしています。また、11月20日の版には、Rubyが11月18日に公表したほかの6件の修正も入っています。

GitLabをどこで使っているか確認する
自社のサーバーやクラウド（AWSなど）に入れているのか、GitLab.comを使っているのかを確かめます。ソースコードを開発会社に預けている場合は、その会社のGitLabかもしれません。
版と入れ方を確認する
GitLabにログインし、「ヘルプ」から版を確かめます。公式パッケージ（Omnibus）や公式のコンテナか、ソースコードから組み立てたものかも確認しましょう。
使っている系統の最新版に更新する
上の表の「移る先」まで上げます。19.3以前は19.4.10以上へ。大きく版を上げるときは、GitLabが決めている途中の版（アップグレードパス）を順に通る必要があります。
ソースから組み立てた場合はRubyも更新する
GitLabを動かしているRubyを3.3.14・3.4.13以上で入れ直します。
あやしい動きがないか確かめる
見覚えのないアカウント、管理者の権限の変更、CI/CDの変数やアクセストークンの作成、Gitalyのプロセスの異常終了がないかを見ます。あやしい点があれば、トークンや鍵を作り直しましょう。

GitLab Critical Patch Release: 19.6.1, 19.5.8, 19.4.10
On November 20, 2026, we released versions 19.6.1, 19.5.8, 19.4.10 for GitLab Community Edition and Enterprise Edition.
These versions contain important bug and security fixes, and we strongly recommend that all self-managed GitLab installations be upgraded to
one of these versions immediately.
GitLab.com and GitLab Dedicated are already running a patched version. GitLab.com and GitLab Dedicated customers do not need to take action.
GitLab Dedicated was previously protected through internal-only releases 19.5.7 and 19.4.9, which contained interim mitigations for these vulnerabilities; all fixes from those releases are also included in 19.5.8 and 19.4.10.
GitLab releases fixes for vulnerabilities in patch releases. There are two types of patch releases:
scheduled releases and ad-hoc critical patches for high-severity vulnerabilities. Scheduled releases are released twice a month on the second and fourth Wednesdays.
For more information, please visit our 
releases handbook
 and 
security FAQ
.
You can see all of GitLab release blog posts 
here
.
We are committed to ensuring that all aspects of GitLab that are exposed to customers or that host customer data are held to
the highest security standards. To maintain good security hygiene, it is highly recommended that all customers
upgrade to the latest patch release for their supported version. You can read more
best practices in securing your GitLab instance
 in our blog post.
Recommended Action
We 
strongly recommend
 that all installations running a version affected by the issues described below are 
upgraded to the latest version as soon as possible
.
When no specific deployment type (omnibus, source code, helm chart, etc.) of a product is mentioned, it means all types are affected.
Important guidance for self-compiled GitLab installations:
 The fix for CVE-2026-132825 is a patch to Ruby. Official GitLab Linux packages and container images already include the patched Ruby. For self-compiled installations, you must rebuild the Ruby installation used to run GitLab with Ruby 3.3.14 or 3.4.13 (or a later release in the same minor series), which include the fixes for CVE-2026-132825 and the other vulnerabilities disclosed in the 
Ruby security advisory
, as described in 
Ruby
