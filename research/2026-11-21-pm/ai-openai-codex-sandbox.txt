At a glance
OpenAI says Codex constrains commands with OS-level sandboxing in your existing environment instead of moving them into a separate container, and posted the design on X on 19 November NZ time.
In a Git workspace, the default profile lets Codex edit source files without approval but blocks writes to the root .git and .codex folders, OpenAI says; the docs add .agents and .aws.
The default profile disables network access, and a command that asks for it goes to you or to auto-review; allowing a registry's domain in a permission profile skips the prompt.
macOS enforces the sandbox with Seatbelt, Linux with bubblewrap plus seccomp, and Windows with MXC, and Codex refuses to run a command on macOS if the platform can't enforce the policy.
With approvals_reviewer set to auto_review, a separate reviewer agent decides eligible approval requests, and a denial tells the main agent to find a materially safer path or ask you.
OpenAI says Codex runs your commands inside an operating-system sandbox on your own machine instead of a separate container, and that the default profile keeps network access off. OpenAI Developers laid out the design in a thread on X on 19 November NZ time, with a link to an OpenAI post titled 
Inside the Codex sandbox
.
The thread’s first post gives the reason: as models get more capable, limits on what they can reach matter more. OpenAI’s example is that a command editing your repo shouldn’t automatically get network access.
As models become more capable, limits on what they can access matter more. A command editing your repo shouldn’t automatically be allowed network access.
The Codex sandbox lets Codex run commands in your existing environment within the filesystem and network limits you control.
— OpenAI Developers (@OpenAIDevs) 
November 18, 2026
What the default profile allows
When a Git repository is the workspace for a Codex session, the default permission profile lets Codex edit source files without asking, but blocks writes to the root .git and .codex folders, OpenAI says. It also allows broad reads across the filesystem. The 
approvals and security docs
 add that .agents and .aws get the same protection when they exist, and that it’s recursive, so everything under those folders is read-only.
The default profile lets Codex edit your code and keeps .git, .codex and the network closed.
A permission profile is a named policy that pairs filesystem rules with network rules. Codex ships three built-in ones: 
:read-only
, 
:workspace
 and 
:danger-full-access
, which removes the local sandbox restrictions. You can write your own under 
[permissions.<name>]
, or start from a built-in with 
extends = ":workspace"
 so the protected paths stay read-only unless you override them. The 
permissions page
 labels profiles a beta, and says a config uses either profiles or the older 
sandbox_mode
 setting, never both.
Why it uses the OS and not a container
Instead of moving the work into a separate container, Codex has the operating system constrain each command in the environment you already use, OpenAI says. Its example is building an iOS app on a Mac with Codex. The sandbox covers spawned commands, not only Codex’s own file operations, so git, package managers and test runners inherit the same limits, according to the 
sandbox docs
.
Each operating system does the enforcing its own way. On macOS, Codex uses Seatbelt, Apple’s built-in sandbox, and runs commands through 
sandbox-exec
. On Linux it uses bubblewrap (bwrap) plus seccomp, a Linux feature that filters which system calls a process can make. Windows uses MXC, with elevated and unelevated modes kept as legacy fallbacks, and WSL2 uses the Linux version.
Each operating system enforces the same boundary with its own tool.
On macOS, if the platform sandbox can’t enforce the selected policy, Codex refuses to run the command instead of running it unsandboxed, the permissions docs say. Linux users install bubblewrap first. Codex uses the first 
bwrap
 it finds on the path and otherwise falls back to a bundled helper, which needs support for unprivileged user namespaces.
OpenAI wrote up the Windows side on 13 May in 
Building a safe, effective sandbox to enable Codex on Windows
. It says Windows doesn’t provide this kind of isolation out of the box, so OpenAI built its own, and that every Codex command is sandboxed from the start with every descendant process staying inside the same boundary.
Network access stays off until you open it
The default profile disables network access. When a command asks for it, Codex can prompt you directly or route the request to auto-review, OpenAI says. If your build regularly downloads from a package registry, you can allow that registry’s domain in a permission profile and skip the prompt.
A blocked network request goes to you or auto-review, unless a profile already allows the domain.
Two settings do the work. 
network.enabled = true
 in a profile lets commands reach the network, and 
features.network_proxy = true
 makes Codex enforce the profile’s domain rules. With the network on and the proxy off, commands connect directly with no domain limits. In the domain list, 
"example.com"
 matches that exact host, 
"*.example.com"
 matches subdomains only, 
"**.example.com"
 matches the apex and its subdomains, and a deny rule beats an allow rule.
OpenAI’s permissions docs show a profile that builds on 
:workspace
, keeps matching .env files denied and allows one API domain:
Code
Copy
default_permissions = "project-edit"
[features]
network_proxy = true
[permissions.project-edit]
description = "Project editing with OpenAI API access."
extends = ":workspace"
[permissions.project-edit.filesystem.":workspace_roots"]
"**/*.env" = "deny"
[permissions.project-edit.network]
enabled = true
[permissions.project-edit.network.domains]
"api.openai.com" = "allow"
Auto-review answers the prompts
Auto-review
 picks who answers an approval prompt, and it doesn’t move the sandbox boundary. With 
approvals_reviewer = "auto_review"
, Codex sends eligible approval requests to a separate reviewer agent instead of stopping for you. If the reviewer approves, the command runs. If it denies, the main agent is told to find a materially safer path or stop and ask you. Actions the profile already allows run without review.
The docs list what triggers a review: requests for escalated sandbox permissions, commands that match a rule set to prompt, network requests to destinations that need approval, file edits outside the writable roots, and MCP or app tool calls that need approval. The reviewer is built to block sending private data, secrets or credentials to untrusted destinations, probing for credentials, tokens or cookies, broad or lasting security weakening, and destructive actions that risk irreversible damage.
OpenAI applies the same limits to its own deployment. In its 8 May post 
Running Codex safely at OpenAI
, it says it doesn’t give Codex open-ended outbound access: its managed network policy allows expected destinations, blocks others and requires approval for unfamiliar domains.
Test a profile before you rely on it
The Codex CLI has a 
sandbox
 command that runs a command under a profile so you can see what gets blocked. It’s also available as 
codex debug
, and the macOS version also takes a 
--log-denials
 flag.
Code
Copy
# macOS
codex sandbox macos [--permissions-profile <name>] [--log-denials] [COMMAND]...
# Linux
codex sandbox linux [--permissions-profile <name>] [COMMAND]...
# Windows
codex sandbox windows [--permissions-profile <name>] [COMMAND]...
The full profile syntax, including filesystem globs and the managed settings for organisations, is on the 
permissions page
.

OpenAI details how Codex runs commands inside limits users set
Michael Bolin's engineering post explains a sandbox built on each operating system's own tools, with file and network rules that users and administrators control.
AI Insiders Staff
EDITED BY  
ALESSANDRO BENIGNI
PUBLISHED

3 MIN READ
Follow on Google
YESTERDAY
OpenAI published a detailed account on 18 November of how its Codex coding agent runs commands on a user’s own computer without free rein. Michael Bolin, a member of technical staff at OpenAI, wrote the engineering post, titled “Inside the Codex sandbox.” The short version: every command the agent launches sits inside rules about which files it may touch and which servers it may reach.
A sandbox is a restricted room for a running program. The program can only use what the room’s rules allow. Bolin’s example is a photo-sorting job, where commands may change files in ~/Pictures while the network stays off, so nothing can be uploaded. A code review might instead get online documentation but leave source files untouchable. Users write these rules as permission profiles.
The built-in 
 profile is deliberately cautious. Commands can write inside the project folder, but directories such as .git and .codex stay read-only, so the agent cannot quietly rewrite Git hooks or its own configuration. Reads are broad across the machine, because compilers and build tools need libraries that live outside the repository. The network is off. That blocks uploads, and it also blocks downloading dependencies.
OpenAI is candid about the gaps. Broad reads mean config files holding API keys may remain visible to a command. Bolin also describes an attack the sandbox does not stop: an agent could plant malicious code in node_modules/prettier, a folder Git often ignores. If the user’s editor then runs Prettier on save, the code executes outside the sandbox. OpenAI’s answer is defense in depth, pairing the sandbox with training and alignment of the model.
OpenAI chose not to use virtual machines or containers. In Bolin’s example, running Codex inside Docker would stop it from using the iOS build toolchain of native Mac programs or launching the iPhone simulator. So Codex leans on each operating system’s own enforcement instead. Child processes inherit the sandbox, which means the limits hold across everything a command spawns.
Network control runs through a proxy. A profile can block all traffic, allow all of it, or send requests through a proxy that checks domain rules. One example allows *.openai.com and localhost while denying evil.example, and a deny always beats an allow. A request to an unlisted domain can pause for approval from the user or from auto-review. The proxy looks up a hostname only after approving it, since even a DNS lookup can leak data encoded in the name. OpenAI notes that very broad wildcards, or access to DNS services, can still allow that kind of leak.
Enforcement differs by platform. On macOS, Codex uses Seatbelt through the sandbox-exec command, which Apple’s manual page labels deprecated; OpenAI says it will keep using it, noting that Google Chrome and Chromium rely on it too. On Linux, Codex combines bubblewrap with seccomp-bpf, a kernel filter for system calls. On Windows, OpenAI is replacing its earlier sandbox with one built on MXC (Microsoft eXecution Container), citing the old design’s need for admin access during setup and slow permission checks.
Enterprises get a lever of their own. Administrators can set requirements.toml to limit which profiles employees may choose, for instance allowing 
 while forbidding 
. Cloud requirements outrank the system file at /etc/codex/requirements.toml.
Developers outside OpenAI can reuse the machinery. The codex sandbox command wraps any command in a profile. Bolin shows it confining the memory MCP server, pinned at version 1.0.0, so it writes only to the npm cache and its data folder, with no network.
All of this comes from OpenAI’s own description, and the post cites no independent testing. The candid part is the useful part: reads are wide open by default, and writes are where the guardrails sit. Before letting any agent loose on a laptop, list the secrets it could read and the folders it could poison, then write profile rules for those first.

Inside the Codex sandbox
How Codex runs commands on your machine with limits you control.
By Michael Bolin, Member of Technical Staff

At OpenAI, we take a 
defense in depth
⁠
(opens in a new window)
 approach when it comes to safeguarding agents. While our investments in training and alignment are fundamental to this effort, we also implement features in our agentic harness, 
Codex
⁠
(opens in a new window)

Codex sandbox
 so Codex can work in your existing environment within filesystem and network limits you control.
A
⁠
(opens in a new window)
sandbox
⁠
(opens in a new window)
 limits what a program can access while it runs. For a photo-organizing task, you might configure the Codex sandbox to let commands read and modify files in

⁠
(opens in a new window)

In this article, we’ll start with the tradeoffs behind Codex’s sandbox defaults, then explain the sandbox’s design and how the harness uses it to run commands. We’ll show how end users and enterprises can tailor its permissions to their needs and how developers can reuse the sandbox in their own tools. Finally, we’ll examine how these restrictions are enforced on macOS, Linux, and Windows.
Choosing the sandbox boundaries
In Codex, our philosophy is to specify conservative defaults for the sandbox that still enable meaningful work. For example, with a Git repository as the workspace root, the built-in 
:workspace
 permission profile:
Allows writes within the workspace, while keeping directories such as 
.git
 and 
.codex
 read-only.
 This lets Codex edit source code without seeking permission for every change, while preventing direct changes to 
.codex/config.toml
 or Git hooks under 
.git/hooks
.
Allows broad filesystem reads, subject to the user’s existing OS permissions.
 Compilers, runtimes, and build tools depend on SDKs, libraries, and configuration outside the repository. Restricting reads to the workspace would break many ordinary workflows. The tradeoff is that sensitive files elsewhere on the machine may also remain readable (such as config files containing API keys).
Disables network access.
 This blocks direct uploads to external services, including attempts to exfiltrate data the command can read. It also prevents legitimate operations such as downloading dependencies, which require additional access.
These restrictions prevent a large class of bad behavior, but harmful actions are still possible. For example, the agent could inject malicious code into a locally installed package such as 
node_modules/prettier
. Such a change might not appear in 
git status
 because 
node_modules
 is often ignored by Git. If the user’s editor runs that copy of Prettier on save, simply saving a file could execute the malicious code outside the Codex sandbox. This is why we take a defense in depth approach: the sandbox limits what commands can access, while training and alignment help the model use that access in accordance with the user’s intent.
For guidance on tailoring sandbox permissions and combining them with other protections in an enterprise environment, see the
Codex security cookbook
⁠
(opens in a new window)
.
Designing the s
andbox
Virtual machines and 
containers
⁠
(opens in a new window)
 are two popular mechanisms used for sandboxing, but we take a different approach with the Codex sandbox. Instead of moving computation to a separate environment to provide isolation, Codex uses each platform’s sandboxing facilities to constrain commands running in the user’s existing environment.
For many developers, their laptop serves as a bespoke dev environment that they can change on a whim. Reproducing that environment in a Docker container can take work, and some workflows still depend on tools that run on the host.
For example, consider using Codex to develop an iOS app on a Mac. If you decided to sandbox Codex by running it inside Docker, Codex would not be able to run the iOS build toolchain composed of native Mac executables, nor could it launch the iPhone simulator to run the code. A Docker-based workflow could delegate builds and simulator operations to the Mac host, but those operations would execute outside the container’s sandbox and would need their own restrictions. For Codex, we prefer to keep things simple by investing heavily in OS-specific sandboxing so Codex can run in the environment that is most appropriate to the task at hand.

Codex sandbox implementation
The sandbox implementation turns a permission profile into restrictions enforced by the operating system. The network proxy’s core request-handling and policy logic is shared across all three major operating systems, while proxy setup and integration with the sandbox are OS-specific. We’ll examine the shared proxy first, followed by the implementations for macOS, Linux, and Windows.
Network proxy
To enforce a permission profile’s network restrictions, the harness starts a network proxy and configures the sandbox to allow connections to it while blocking direct connections to external hosts. The proxy checks each request against the profile’s domain rules to determine whether to forward it.
