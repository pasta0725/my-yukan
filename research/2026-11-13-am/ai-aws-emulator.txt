AWS has released an emulator that kind-of-almost lets you use its cloud on a PC.
As explained in the 
GitHub repository
 for the prosaically named “AWS Emulator,” the tool “is a local program that serves an AWS API endpoint.”
The emulator doesn’t replicate the whole AWS cloud, instead offering its APIs.
REG AD
“You use it to test your software without calling AWS, on your own machine, on a development server, or in continuous integration (CI),” the repo explains. Because those tests never touch the AWS cloud, the tool is free to use.
REG AD
AWS wrote the emulator in Rust, a choice that senior specialist solutions architect Daniel Abib wrote helps to ensure the tool “stays light on CPU and memory on a laptop.”
The emulator tool doesn’t replicate the entire AWS cloud. Abib said it supports the APIs of AWS services that have an API model in the 
AWS API models repository on GitHub
. 
The Register
 found over 1,300 items on that page.
While the tool lets developers test APIs, it doesn’t replicate anywhere near all the features of the Amazonian cloud.
“It doesn’t evaluate IAM [Identity and Access Management] policies the way AWS does, and each emulator acts as a single account, with no cross-account or cross-Region behavior,” Abib wrote, adding “How closely it matches AWS varies by service and feature.”
AWS publishes “fidelity scores” that detail how closely the emulator works on different AWS services. Amazon tries to achieve full fidelity, so the emulator produces the same results as AWS for valid API calls, and the same errors for invalid ones.
Coding agents can also drive the Emulator, an option 
The Register
 mentions because AWS 
advises
 the easiest way to check if a project will work with the tool is to use the 
aws-emulator
 skill for AI coding agents.
“With the skill, your agent finds the AWS operations and resources that your project depends on. It checks them against the fidelity tests and fidelity scores for the emulator. It then tells you which parts of your project you can rely on the emulator for, and which ones might behave differently from AWS,” according to AWS documentation.
AWS has made the emulator available as an RPM or Debian package. Mac and PC users will need to run Docker and an image of the Emulator.
REG AD
“You install the emulator, start it, and point your tools at the local endpoint,” Abib instructed. “When AWS Emulator starts, it generates its own credentials, a config file, and a certificate, and writes them to 
~/.aws/emulator/9297/
. You set environment variables so the AWS SDK talks to your laptop instead of AWS, and your application code stays unchanged.”
“From there, your existing tests, CLI scripts, and coding agents keep working the way they already do. A unit test that creates an 
Amazon DynamoDB
 table, writes an item, and reads it back is the same test, and it runs on your machine without a deployment.”
The cloud colossus’s intent appears, as ever, to encourage more use of its cloud – in this case by satisfying developers their code will run well when deployed there, and making it easy for them to test for that. ®

I'm Ishikawa from the Cloud Business Division. On November 11, 2026, AWS Emulator, a local emulator for AWS APIs, became generally available. I ran AWS Emulator on macOS and compared it with real AWS to check the claims about AWS Emulator in the contribution by Swami Sivasubramanian that was published on All Things Distributed the same day.
https://www.allthingsdistributed.com/2026/11/aws-emulator-and-the-engineers-job-when-agents-write-the-code.html
https://aws.amazon.com/about-aws/whats-new/2026/11/aws-emulator-now-available/
Werner Vogels's blog All Things Distributed published a contribution by Swami Sivasubramanian, "AWS Emulator and the engineer's job when agents write the code". Its claims can be summarized in three points.
Claim 1
: A coding agent repeats a cycle: write code, run it, read the result, and decide the next change. If the services it calls behave like the real ones, the agent can verify its work as it writes, and the share of code that is correct the first time goes up. AWS Emulator provides that verification target on your own machine
Claim 2
: For AWS Emulator, agents fixed fidelity tests built from the public API models until they passed against real AWS, and then implemented the emulator until it passed those tests. One example given is that in Amazon SQS, a received message stays invisible to other consumers until the visibility timeout
Claim 3
: When agents write the code, the engineer's job is to let the agent work autonomously, and for that the engineer designs specifications, tests, and merge gates
In this article I check claims 1 and 2 by asking "does it return the same results and errors as real AWS?", and claims 1 and 3 by asking "if you prepare the spec and tests first, can you repeat write, run, and read the result locally?".
https://docs.aws.amazon.com/emulator/latest/userguide/what-is-service.html
https://aws.amazon.com/blogs/aws/test-your-applications-against-aws-locally-with-aws-emulator/
 What is AWS Emulator
AWS Emulator is a program that serves AWS APIs on a local HTTPS endpoint. If you switch the request destination of the AWS CLI or AWS SDK to this endpoint with an environment variable, requests are not sent to AWS but are processed against resources in the emulator's memory. No AWS account is required and there is no additional service charge. The source code is published on GitHub under CC0 1.0 Universal.
https://github.com/aws/aws-emulator
The position of AWS Emulator as seen from the AWS CLI or AWS SDK is as follows.
As a test target, the differences from real AWS are as follows.

The main specifications are as follows.
On Linux, install it with an RPM or Debian package. On macOS and Windows, build an image from the Dockerfile in the documentation and run it in a container (no prebuilt image is published)
By default it serves HTTPS on 
127.0.0.1:9297
. At every startup it generates credentials, a config file, and a certificate under 
~/.aws/emulator/<port>/
, and requires requests to be SigV4-signed with that key
One emulator acts as one account (
000000000000
) and keeps resources only in memory. Resources disappear when it stops
Each service is generated from the same public API models as the AWS SDK. Supported operations return the same results and errors as AWS, and unsupported operations return 
501 Not Implemented
The degree of agreement with AWS (fidelity) is published with each release, using the number of passed fidelity tests as the fidelity score
It does not evaluate IAM policies the way AWS does. It cannot be used for security testing or production workloads
Sending anonymous usage data (telemetry) is enabled by default. You can disable it with 
--telemetry off
https://docs.aws.amazon.com/emulator/latest/userguide/fidelity.html

Test your applications against AWS locally with AWS Emulator
Today we’re announcing AWS Emulator, a local emulator for Amazon Web Services (AWS) that you run on your machine. The 
AWS Command Line Interface (AWS CLI)
, the 
AWS SDKs
, and your coding agents speak to it over a local HTTPS endpoint using the same AWS APIs they would use in the cloud, from your laptop. AWS Emulator has no additional service fee. You pay only for AWS resources when you deploy on AWS. Its source is on 
GitHub
. You install it from an RPM or Debian package on Linux, and on macOS and Windows you run it in Docker.
How it works
         You install the emulator, start it, and point your tools at the local endpoint. When AWS Emulator starts, it generates its own credentials, a config file, and a certificate, and writes them to 
~/.aws/emulator/9297/
. You set environment variables so the AWS SDK talks to your laptop instead of AWS, and your application code stays unchanged.
From there, your existing tests, CLI scripts, and coding agents keep working the way they already do. A unit test that creates an 
Amazon DynamoDB
 table, writes an item, and reads it back is the same test, and it runs on your machine without a deployment. A coding agent can create resources, check the result, and iterate again without waiting on a deployment in a Region.
The emulator is implemented in Rust so that it stays light on CPU and memory on a laptop. It supports the APIs of AWS services that have an API model in the AWS API models repository on GitHub, and because it’s built from those models, the same ones the AWS SDKs use, your requests and the errors you get back have the same shape as on AWS.
If you are a developer, especially one working with coding agents such as Kiro or Claude Code, you can use that loop to test AWS interactions of real complexity locally.

Using the emulator in process
         Running the emulator as a local process gives you an HTTPS endpoint that works with the AWS CLI and the AWS SDKs through environment variables. Some SDKs need an extra setting to trust the emulator certificate, for example a trust store for the 
AWS SDK for Java
. For tests, there is a second option. AWS Emulator ships an embedded mode that you instantiate directly inside your test process and wire into the SDK through its HTTP client, rather than talking to a separate server over the network. Each embedded instance keeps its own state, so tests do not share buckets, tables, or queues, and you can run many of them in parallel. Embedded mode is available for the 
AWS SDK for Rust
. You add the 
aws-emulator-embedded
 crate from GitHub to the 
[dev-dependencies]
 section of your 
Cargo.toml
 file. The following example creates an Amazon DynamoDB table, writes an item, and reads it back, entirely in process.
use aws_emulator_embedded::{AwsEmulatorEmbedded, EmbeddedOptions};
use aws_sdk_dynamodb::types::{
    AttributeDefinition, AttributeValue, BillingMode, KeySchemaElement, KeyType,
    ScalarAttributeType,
};
#[tokio::test]
async fn put_then_get_returns_the_item() {
    let emulator = AwsEmulatorEmbedded::new(EmbeddedOptions::default());
    let config = aws_config::defaults(aws_config::BehaviorVersion::latest())
        .http_client(emulator.http_client())
        .region(aws_config::Region::new("us-east-1"))
        .credentials_provider(emulator.aws_credentials_provider())
        .load()
        .await;
    let ddb = aws_sdk_dynamodb::Client::new(&config);
    ddb.create_table()
        .table_name("emulator-demo-table")
        .attribute_definitions(
            AttributeDefinition::builder()
                .attribute_name("id").attribute_type(ScalarAttributeType::S)
                .build().unwrap())
        .key_schema(
            KeySchemaElement::builder()
                .attribute_name("id").key_type(KeyType::Hash)
                .build().unwrap())
        .billing_mode(BillingMode::PayPerRequest)
        .send().await.unwrap();
    ddb.put_item()
        .table_name("emulator-demo-table")
        .item("id", AttributeValue::S("item-1".into()))
        .item("msg", AttributeValue::S("hi".into()))
        .send().await.unwrap();
    let got = ddb.get_item()
        .table_name("emulator-demo-table")
        .key("id", AttributeValue::S("item-1".into()))
        .send().await.unwrap();
    assert_eq!(got.item().unwrap().get("msg").unwrap().as_s().unwrap(), "hi");
}
When it runs as a local process, the emulator requires every request to be signed with Signature Version 4 (SigV4), the same way AWS does, and it exposes a 
/__admin/health
 endpoint on the same port so a script or a container can wait until it is ready before running tests. By default it also sends anonymous usage and error data, and you can turn it off.
How we measure fidelity
         An emulator is only useful if a test that passes against it would also pass against AWS, so we measure that directly with fidelity tests. A fidelity test is a short program that uses an AWS SDK to run a workflow, such as storing an object and then reading and deleting it, and asserts how AWS behaves. We verify each fidelity test against real AWS. A fidelity test passes only if the emulator matches AWS on the response to every call, including the status code, the body, and the exact error code and message, and on the resources and data that the workflow creates.
With each release, we publish how many fidelity tests pass for each service, as k of n. For example, 40 of 50 means that 40 of the service’s 50 fidelity tests pass. The set of fidelity tests is public in the aws-emulator-evaluation-suite repository on GitHub, including the ones that don’t pass yet, so you can see what we verified and run the fidelity tests yourself. Read a score as a snapshot of a product that’s improving. When we add fidelity tests, a score can go down even while the emulator gets better.
If the emulator doesn’t implement an operation yet, it returns HTTP 501 (Not Implemented), so your tests fail right away. If the emulator acts differently from AWS, you can tell us by opening an issue in the AWS Emulator repository on GitHub.
How the emulator is built
         AWS Emulator is built and maintained by agents from the AWS API models using 
Amazon Bedrock AgentCore
 Runtime Instances, 
AWS CodePipeline
, and 
AWS CodeCommit
, so it stays current with AWS as those models change.
One group of agents looks for gaps, both by comparing emulator responses against real AWS and by statically comparing the emulator’s code against the published Smithy models, and files an issue for each gap it finds. Another group picks up an issue, writes tests, implements the behavior, and reviews the change for correctness, performance, and security. When the change is ready, it is pushed to a source repository, and that push triggers an AWS CodePipeline run that runs the fidelity tests before the change is published to the public GitHub repository.
How we keep it secure
         Because the code is written by agents, an independent security agent reviews changes adversarially, both while the fix is being made and again in the release pipeline as a final check before anything ships.
Security of your own use remains a shared responsibility. We build the emulator to run safely on your machine: it listens only on your own computer by default and rejects requests that aren’t signed with its own keys. You decide where it runs, what data you put in it, and how you test before production. Don’t use the emulator to test whether your application is secure. It doesn’t evaluate 
AWS Identity and Access Management (IAM)
 policies and resource-based policies the way AWS does, so a request that AWS denies might succeed in the emulator. Keep real credentials out of the environment of your test jobs, and test your security settings and your whole application on AWS before you go to production.
Now available
         AWS Emulator is generally available today. It has no additional service fee. You pay only for AWS resources when you deploy on AWS. You can install it from RPM or Debian packages on Linux, run it in Docker on macOS and Windows, or build from source, and it works with the AWS SDKs and the AWS CLI once you set environment variables. At launch, it has some limits. It doesn’t evaluate IAM policies the way AWS does, and each emulator acts as a single account, with no cross-account or cross-Region behavior. How closely it matches AWS varies by service and feature. To see how well the emulator covers the services that you use, check the fidelity scores in the AWS Emulator documentation.

AWS Capabilities by Region

AWS MCP Server
 and 
plugins

How three teams of AI agents build AWS Emulator
AWS Emulator is fundamentally built by three teams of agents. One team manages a test suite; one team finds issues in the emulator; and one team fixes those issues. We divide agent responsibility into these teams because we’ve found they have more success on bounded tasks.
A graphic showing how teams of AI agents work together to run tests and solve issues.
The first team’s test suite measures fidelity against the real AWS cloud. Each test is a real-world AWS scenario. For example, a test for Amazon SQS might include creating a queue, sending a message, receiving it, acknowledging it, and deleting the queue. Agents devise these tests from publicly released AWS API Models and verify each one against real AWS before submitting. We have tens of thousands of fidelity tests across all of AWS, and that test suite constantly grows as our agents discover new things that they can do with AWS. These tests are one of our most fundamental guardrails in our system because they provide an unambiguous goal that the agents need to meet and can be rerun repeatedly without calling AWS again.
The second team of agents replays the fidelity tests to find divergence in the emulator. When the system initially created the repository, it generated an empty web server that could handle requests for the 438 AWS API Models but did nothing. The agents swarm the repository to figure out what doesn’t work. To kickstart the process, the first issues simply say “build a first version of Amazon SQS.” Once the service is bootstrapped, the agents replay the fidelity tests and file issues for the failing tests. They’re told to reason about the failures and group failures that may share a root-cause.
Each issue is given to an agent in the third team, whose job is to fix that single issue. They check out the code, root-cause the issue, and edit the code until it’s addressed. They must then pass their code change through a gate that ensures it meets our bar. This gate obviously blocks changes that don’t compile. But it also includes agents that review against coding standards, verify the code is secure, and ensure that the change did not regress fidelity. If any of those checks fail, the change is sent back to the agent for rework; if they all pass, it is merged to mainline. We’ve seen thousands of issues fixed every day as hundreds of agents concurrently work on the codebase. Without this merge gate, we wouldn’t trust what our agents are building. We focus a lot on optimizing it because it’s so critical to how quickly and reliably the agents build.
