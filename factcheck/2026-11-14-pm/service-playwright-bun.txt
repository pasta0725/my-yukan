テストフレームワーク「Playwright」がBunを正式サポート。テストランナーの実行を可能に
2026年11月12日
Webアプリケーションのテストフレームワーク「Playwright」が、最新バージョンのv1.65.0で、Bunでのテストランナー実行を
正式にサポートしました
。
PlaywrightのテストランナーはこれまでNode.jsが用いられていました。今回、そのNode.jsに加えて、Bunでのテストランナーの実行を正式にサポートしました。
BunがTypeScriptをトランスパイルしてくれる
GitHub上のPlaywrightリポジトリにはv1.65.0について以下のように説明されています。
The test runner now runs under Bun. Bun transpiles your TypeScript test files itself, so Playwright does not use Babel or its compilation cache.
テストランナーはBun環境下で実行されます。BunがTypeScriptテストファイルをトランスパイルするため、PlaywrightはBabelやコンパイル関係のキャッシュを使いません。
PlaywrightではTypeScriptを用いてテストケースを記述できます。これまではこのTypeScriptをトランスパイルし、その結果を保持するためにBabelやコンパイルキャッシュが用いられていました。
しかし上記の説明にもあるように、テストランナーにBunを用いることでBunのトランスパイル機能を利用することができるため、Babelが不要となりシステムがシンプルになる利点が得られます。
ただし、Watch Modeがない、UI Modeがファイル変更時に自動再実行しない、「--only-changed」の挙動に制限がある、「--tsconfig が効かない」など、Node.jsを用いた場合と比較していくつか非互換部分がある点には注意が必要です。
BunはすでにPlaywrightを実行可能だったが……
Bunは今年（2026年）8月にリリースしたBun 1.4において、Playwrightの実行が可能になったと説明していました。
参考：
Rustに移植された「Bun 1.4」正式リリース。Node.jsとの互換性向上でPlaywrightやvitestが動作、CPUとメモリの使用率が大幅改善、正規表現が高速化など
これはあくまでもBunがNode.jsとの互換性を高めた結果、Playwrightの動作が可能になったということです。そのためこの時点ではあくまでも非公式にPlaywrightでBunを使うことが可能になった、ということでした。
しかし今回、Playwrightが正式にBunのサポートを発表したことで、今後は安心してPlaywrightでBunを利用できるようになった、ということになります。

Playwright 1.65 in CI: Breaking Changes, Bun and Reports
Walter Galvão
 |
Nov 09, 2026
 |
TL;DR
This article covers what changes for CI when you upgrade to Playwright 1.65: the new failures reporter and onlyFailures option, the built-in exclusive test lock, and running the test runner under Bun. It also covers the breaking changes that can turn a green suite red without a single test changing, such as class fields in page objects, sharded runs that match no tests, blob report directories and inert elements.
Move CI's Node.js version to 22, 24 or 26 in the same pull request as the Playwright bump.
Move locator initializers into page object constructors, and give each blob invocation its own directory.
Add 
--pass-with-no-tests
 only where a filter can legitimately match nothing.
Fix whatever still breaks, and only then turn on the 
failures
 reporter and 
onlyFailures
.
Bump Playwright to 1.65 on a suite that was green, and it can go red without a single test changing. A page object throws as soon as a test builds it, because a field initializer that reads a constructor parameter property now runs before that property is set. Clicks and fills behind an open drawer now wait for the element to stop being inert, and time out if it stays inert. A filtered, sharded run that matches no tests in any shard fails with "No tests found". A pipeline that writes several blob reports into one directory is left with only the last one to merge.
The fixes are a handful of config and pipeline lines you can change before the bump.
What's new in Playwright 1.65
TypeScript class fields now follow 
useDefineForClassFields
 from your 
tsconfig.json
, the same as 
tsc
, so a field initializer that reads a constructor parameter property now fails, because the initializer runs first.
A sharded run now fails with "No tests found" when no tests match across all shards; pass 
--pass-with-no-tests
 to allow this.
The blob reporter again deletes the content of its output directory before it writes the report.
Actions such as 
locator.click()
 now wait for the element to be not inert, and text that the browser does not render is no longer part of accessible names and aria snapshots.
Cookie matching now follows RFC 6265, and proxy credentials are no longer sent to websites: the credentials in the 
proxy
 option now answer only proxy challenges.
String and 
URLSearchParams
 values of the 
params
 option in APIRequestContext requests are now appended to the query that the URL already has.
.css
, 
.less
 and 
.scss
 imports in test files now load as empty modules.
Test locations of imported calls in CommonJS output now point to the start of the callee.
Playwright no longer tests on Node.js 20 (use Node.js 22, 24 or 26), and Docker images now include Node.js 26 instead of Node.js 24.
The test runner now runs under Bun when you pass the 
--bun
 flag, because without it 
bunx playwright test
 runs on Node.js.
A new 
failures
 reporter prints failures and successful retries as they occur, followed by a summary, without progress output, and a new 
onlyFailures
 option of the HTML, JSON and JUnit reporters keeps only tests with unexpected outcomes, flaky tests and interrupted tests.
A new built-in 
-exclusive-
 test lock runs a test only when no other tests are running.
The full list of changes is in the 
Playwright 1.65 release notes
.

onlyFailures
 keeps tests with unexpected outcomes (unexpected passes included), flaky tests even when they pass on retry, and interrupted tests, with every attempt of each kept test. A test that passed on its first attempt is not in the report at all. That is the trade: smaller files, and no record in them of tests that passed on their first attempt.
Turn it on for HTML when report artifacts have grown too big to be worth uploading. A smaller file fixes the upload, not the 
other limits of the HTML reporter on large suites
. The 
PLAYWRIGHT_HTML_ONLY_FAILURES
 environment variable sets it for the HTML reporter, so you can try it on one CI job without editing the config.
Leave 
onlyFailures
 off the JUnit reporter when a CI tool reads pass counts from the JUnit file. With the option on, that tool sees only the tests 
onlyFailures
 kept, and on JUnit the option retains every attempt regardless of 
includeRetries
. Set it on JUnit only when nothing downstream counts passes. If you want the passes on record across runs anyway, 
Currents Test History
 shows how each test performed across runs and branches, and it treats results with the same spec file, project and title as one test, so renaming a test detaches its history.

The exclusive test lock
Some tests need the whole environment to themselves: one flips a global setting, another resets data that parallel tests read. The new built-in 
-exclusive-
 lock runs a test only when no other tests are running, and all other tests continue to run in parallel with each other.
Use it for exactly those tests, and sparingly. While an exclusive test runs, no other test does. Each one adds about its full duration to the run's wall-clock time. Tests that only clash with each other over one shared account can share a named lock instead: tests sharing a lock name never run at the same time, while all other tests continue to run in parallel. Our 1.64 guide covers 
keeping shared-account tests apart with a lock
.
Anti-pattern
Exclusive as a flake fix
A group of flaky tests races over shared state, so someone marks them all exclusive. The failures go quiet. Each of those tests now stalls every other worker while it runs. The race is still in the code.
Fix
Give each test its own data so it can run in parallel, and keep the lock for tests that change something every other test depends on.

What changes under Bun
Bun transpiles your TypeScript test files itself, so Playwright uses neither Babel nor its compilation cache. The new 
PLAYWRIGHT_TRANSFORM_CACHE_DIR
 environment variable sets the directory for transpiled test files, for example on a Linux machine shared with other users.
Playwright's own CI runs the test runner tests under Bun 1.4.3 on Linux. If you adopt Bun, pin that version and use Linux runners.
Some features work differently under Bun, and these are the ones a pipeline feels:
--tsconfig
 and the JSX options in 
tsconfig.json
 have no effect, because Bun loads modules itself.
Custom ESM loaders are not supported.
Stack traces do not include async frames.
API names drop the class name (
click
 instead of 
locator.click
), which changes some step locations, step titles and error messages.
Console output of a test does not get into the trace or UI mode.
Locally, there is no watch mode, and 
--only-changed
 does not follow imports.
When to skip it
Skip Bun if you 
debug CI failures from traces
 and need the test's console output in them, or if your setup depends on 
--tsconfig
 or a custom ESM loader. Also skip it if anything compares step titles or error messages across runs, since API names drop the class name under Bun, which changes some step titles and error messages. Otherwise, try it on one Linux job before moving the rest.
Empty shards and blob reports
The new "No tests found" failure is narrower than it sounds. An empty shard still passes when other shards have tests, and a sharded run fails with "No tests found" when no tests match across all shards.
That happens when a filter matches nothing in the whole suite, such as a nightly 
--grep
 for a tag no test carries yet. Add 
--pass-with-no-tests

# The @experimental tag may be on no test yet, so this job allows an empty match
npx

 @experimental

. Prefer the constructor fix. The tsconfig switch changes how every class field compiles only to rescue a few page objects, and it has a trap of its own. One user reported that a decorated class with a static field fails to load in 1.65 with useDefineForClassFields set to false (
#43936
). The issue was closed as completed on 2026-11-05, with no release named.
Inert elements and accessible names
Expect new timeouts in tests that act on the page while a modal or drawer is open. 
locator.click()
, 
locator.check()
, 
locator.tap()
, 
locator.fill()
, 
locator.clear()
 and 
locator.selectOption()
 now wait for the element to be not inert. An action on an element with the 
inert
 attribute, or inside such an element, now times out if the element stays inert.
Anti-pattern
Raising the timeout
Clicks start timing out after the upgrade, so someone raises the action timeout. If the element stays inert, the action times out at any timeout, and the run only takes longer to fail.
Fix
Close the overlay in the test, or finish the step inside it, before acting on the page behind it.
Accessible names
The same release changes what role locators and aria snapshots see. Text that the browser does not render, such as text that is not assigned to a slot or text directly inside a closed 
<details>
, is no longer part of accessible names and aria snapshots. That can change the results of 
page.getByRole()
 with a name, 
locator.ariaSnapshot()
 and 
expect(locator).toMatchAriaSnapshot()
.
Review those diffs one by one instead of bulk-updating snapshots. A role locator with a name that stopped matching after the upgrade may have matched text the browser does not render.
Other breaking changes to check
The rest are smaller, but each can fail a test far from the feature it changes.
Node.js and browsers
Playwright no longer tests on Node.js 20; use Node.js 22, 24 or 26, as listed in the system requirements. Move CI's Node.js version in the same pull request as the Playwright bump. Docker images now include Node.js 26 instead of Node.js 24, and the latest patch of Chromium on the same branch. The 1.65 browsers are Chromium 158.0.8127.18, Firefox 159.0 and WebKit 27.2.
Cookies and requests
Cookie matching now follows RFC 6265. With a URL, 
browserContext.cookies()
 and 
apiRequestContext.cookies()

Path=/api

/apiv2

Path=/foo/

/foo
. That breaks a test that passes a subdomain URL to those calls and expects a host-only cookie back, or passes 
/apiv2
 and expects a 
Path=/api
 cookie. APIRequestContext sends a cookie without a name as 
Cookie: x
 instead of 
Cookie: =x
.
String and 
URLSearchParams
 values of the 
params
 option are now appended to the query that the URL already has, instead of replacing it. That hits an API test whose URL already holds a query string and also passes 
params
 as a string or 
URLSearchParams

params

Check API tests that post string bodies with a JSON content type, too. A regression report against 1.65.0 says that string data that is not valid JSON, sent with an application/json;charset=UTF-8 header, is now JSON-encoded (
#43937
). In 1.64.1, the report says, only an exact application/json header did that. The issue was closed as completed on 2026-11-06.

Upgrade order
Do the bump on a branch with full reports, so you can compare test counts and passes against your last 1.64 run, not just the failures. On that branch, move CI's Node.js version, move locator initializers into page object constructors, give each blob invocation its own directory, and add

What are the breaking changes in Playwright 1.65?

Why does my page object fail after upgrading to Playwright 1.65?

1. Playwright Bun support: run the test runner with bunx --bun
Bun is a JavaScript runtime that also acts as a package manager and bundler. Until now, Playwright's test runner assumed Node.js, even when the rest of a project ran on 
Bun
.
The problem
A team that builds and serves its app with Bun still had to keep Node.js around for 1 job: the end-to-end tests. That means 2 runtimes to install in CI, 2 lockfile habits, and 2 sets of version bumps.
Running 
bunx playwright test
 did not help either. That command quietly starts Playwright on Node.js, so the tests never touched Bun at all.
What Playwright 1.65 does
The test runner now runs under Bun when you pass the 
--bun
 flag. The release notes state that Bun transpiles your TypeScript test files itself, so Playwright does not use Babel or its compilation cache.
                        terminal                    
bunx --bun playwright test
To see which runtime really executes the tests, we added a 1-line check to the demo suite.
                        tests/runtime.spec.ts                    
import { test } from '@playwright/test';
test('print the runtime', async () => {
  console.log(`bun: ${process.versions.bun ?? 'not running under Bun'} | node: ${process.versions.node}`);
});
We ran it twice, once without the flag and once with it.

2. Playwright failures reporter and onlyFailures: reports with only failures
Every Playwright run ends in a report, and most of each report describes tests that passed. Version 1.65 adds 2 separate tools that cut that down: a terminal reporter and a report option.
The problem
The default list reporter prints a line for every test. On CI the default is the dot reporter, which prints a character per test. Both are fine for 50 tests and tiring for 5,000.
Stored reports have the same shape. An HTML report for a large suite carries thousands of green rows around the 3 red ones you opened it for.
What Playwright 1.65 does
The new 
failures reporter
 prints failures and successful retries as they happen, followed by a summary. It prints no progress output at all.
                        terminal                    
npx playwright test --reporter=failures
Here is what it printed for the demo store suite, trimmed to the key lines.

3. Test runner: the -exclusive- lock, description-only skips, and a movable cache
Three smaller runner changes ship in this release. The first replaces a familiar workaround, the separate single-worker job.
The -exclusive- lock
Playwright 1.63 introduced named test locks, so 2 tests that share a resource never overlap. Version 1.65 adds a built-in lock name, 
-exclusive-
, described in the 
test locks docs
.
A test with this lock starts only when no other test is running, and no other test starts until it finishes. Everything else keeps running in parallel with each other.
                        tests/performance.spec.ts                    
import { test, expect } from '@playwright/test';
test('measure product list load time', { lock: '-exclusive-' }, async ({ page }) => {
  const started = Date.now();
  await page.goto('/products');
  await expect(page.getByText('Showing 14 products')).toBeVisible();
  console.log(`product list ready in ${Date.now() - started}ms`);
});

Without this lock, the options were a separate project or a second CI step with 
--workers=1
. Both add a slower path to protect 1 test, which works against

Good candidates are tests that measure timing, restart a shared service, or change a global setting. Anything in a 
Playwright performance testing
 setup is a natural fit, since a busy CPU skews the numbers.
Note:
 In the default and serial modes, all tests in a file run together in order, so a lock on any test is held for the whole file. Put exclusive tests in their own file, or enable 
fullyParallel
, to keep the lock short.
Description-only skips
Until now, giving a reason for a skip inside a test body meant passing a condition first, as in 
test.skip(true, 'reason')
. The condition was noise when the skip was unconditional.
In 1.65, 
test.skip()
, 
test.fixme()
, 
test.fail()
, and 
test.slow()
 accept only a description.
