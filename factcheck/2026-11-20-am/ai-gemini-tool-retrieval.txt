Today we're launching Tool Retrieval in the Gemini API, available in preview in the
 Interactions API
.
When an agent connects to dozens or even hundreds of tools, sending every full parameter schema on every request adds up fast. It inflates input token counts, adds latency, and lowers tool-selection accuracy as the candidate list grows. Tool Retrieval lets your agent keep its full tool library on standby and load parameter schemas only when the current task needs them.
How it works
To turn on Tool Retrieval, add a 
tool_search
 tool to your request and set 
defer_loading: true
 on the tools you want to hold back. The model still sees the name and description of every deferred tool, so it knows what's available, but the parameter schemas stay out of context. When the model needs a tool, it asks for it by name, the API loads the full schema, and the model calls the function, all inside the same request.
from google import genai
client = genai.Client()
tools = [
   {"type": "tool_search"},
   {
       "type": "function",
       "name": "issue_refund",
       "description": "Refund an order to the original payment method.",
       "defer_loading": True,
       "parameters": {
           "type": "object",
           "properties": {
               "order_id": {"type": "string"},
               "amount": {"type": "number"},
           },
           "required": ["order_id", "amount"],
       },
   },
   # ... 50+ other deferred functions (leave frequent tools undeferred)
]
interaction = client.interactions.create(
   model="gemini-4-hydrogen",
   input="Order A-1042 arrived damaged. Please refund 40 dollars.",
   tools=tools,
)
Inside that single API call, the model searches for 
issue_refund
, the API loads its schema, and the model emits the 
function_call
. All three steps appear in 
interaction.steps
, making it easy to inspect which tools the model considered when debugging tool names or descriptions:
"steps": [
 {
   "type": "tool_search_call",
   "id": "tsc_7f2a",
   "arguments": {"function_names": ["issue_refund"]},
   "signature": "..."
 },
 {
   "type": "tool_search_result",
   "call_id": "tsc_7f2a",
   "result": [{"type": "function", "name": "issue_refund", "parameters": {...}}],
   "signature": "..."
 },
 {
   "type": "function_call",
   "id": "fc_91c3",
   "name": "issue_refund",
   "arguments": {"order_id": "A-1042", "amount": 40}
 }
]
From here it's normal function calling: your code runs the refund and sends back a 
function_result
.
There's no index to build or host. Gemini runs the search on the server, so the only changes to your code are the new tool and a flag on the tools you want to defer. You can keep your most-used tools loaded up front and defer the long tail.
Tool Retrieval also plays well with prefix caching. Deferred schemas stay out of the start of the prompt, and the schemas the model loads are added later in the conversation, so the cached prefix stays the same from turn to turn.
Tool Retrieval also works with 
remote MCP servers in the Gemini API
. Set 
defer_loading: true
 on an 
mcp_server
 tool and every tool that server exposes is loaded on demand, so you can connect a large server without listing its tools one by one.
How client-side retrieval works
If you maintain your own tool registry, embedding index, or per-user permission filter, declare the 
tool_search
 with 
"execution": "client"
 and define your search parameters. Client-side retrieval adds one round trip per search, because your app runs the lookup. Tools do not need to be declared upfront, so you can also expose new tools mid-conversation when a user connects an integration:
tools = [{
    "type": "tool_search",
    "execution": "client",
    "name": "search_tools",
    "description": "Search the internal tool registry for functions.",
    "parameters": {
        "type": "object",
        "properties": {"query": {"type": "string"}},
        "required": ["query"],
    },
}]
# When the model emits a function_call for "search_tools",
# return matching {"type": "function", ...} schemas in function_result:
followup = client.interactions.create(
    model="gemini-4-hydrogen",
    previous_interaction_id=interaction.id,
    tools=tools,
    input=[{
        "type": "function_result",
        "name": "search_tools",
        "call_id": step.id,
        "result": my_registry.search(**step.arguments),
    }],
)
How pricing and supported models work
Tool Retrieval has no separate charge. Input and output tokens are billed at the standard rates for the model you call. Turning on 
tool_search
 adds a small, fixed block of input tokens, and each schema the model loads is billed as input for the rest of the conversation, the same as a tool declared up front. You save tokens when the schemas you never load outweigh the ones you do, which is the usual case for large libraries. Measure it against your own traffic.
Tool Retrieval works with Gemini 3.6 and later models, including 
all Gemini 4 models
, in the Interactions API.

Google
 has launched Tool Retrieval in the Gemini API, a preview feature built for AI agents that juggle a lot of tools at once.
It lives inside the Interactions API. It targets a problem that grows with every tool a developer adds: agents get slower, cost more to run, and get worse at choosing the right tool.
What Tool Retrieval actually fixes
Start with how agents use tools. An AI agent can call outside functions, such as a search engine, a file lookup, or a custom piece of business logic.
To pick the right one, the model needs to know what each tool does and what inputs it expects. That description is called a parameter schema, and it is basically the tool’s instruction manual.
Until now, an agent wired to dozens or even hundreds of tools would send every one of those full schemas along with every request. Google says this approach piles up quickly.
Advertisement
Google points to three specific costs of the old approach:
Inflated input tokens.
 Every schema counts toward what the model reads, and models bill by the token.
Added latency.
 More text to process means a slower response.
Lower tool-selection accuracy.
 As the candidate list gets longer, the model gets worse at picking the correct tool.
Tool Retrieval changes the default. Rather than shipping the full parameter details for every tool on every call, the system retrieves only the relevant schemas when they are needed.

Where it fits in Google’s developer stack
Tool Retrieval is part of a broader push by Google to make tool use a first-class feature of the Gemini API.
The API already ships with built-in tools, including Google Search, File Search, and Code Execution. Developers can also bring their own functions through custom function calling.
The Interactions API is the home base for all of it. It reached general availability in mid-2026 and is the preferred interface for new applications built on Gemini.
Its design leans into multi-turn workflows and server-side state management. Translated: the API is built for conversations and tasks that unfold over many steps, with Google keeping track of the running context on its side rather than forcing developers to resend everything each time.
The feature also follows other recent upgrades. In May 2026, Google rolled out multimodal enhancements to File Search, part of the same steady stream of improvements aimed at developers building agent-driven applications.
What this means for developers building agents
The clearest impact lands on teams running large, tool-heavy agents. Those are the setups where full-schema requests hurt most, since the overhead scales with the number of tools connected.
There are caveats worth keeping in mind. The feature is in preview, which generally means behavior, availability, and interfaces may change before a stable release.
Developers will also want to see how retrieval performs in practice. Any system that decides which tools to surface introduces its own failure mode: if the retrieval step misses the right tool, the model never gets a chance to pick it.
Things to watch from here include how Google prices the feature and whether it moves from preview to general availability.

The search, schema load and function call appear in `interaction.steps`, which developers can inspect when debugging tool names or descriptions. After that, function calling works as usual: the application runs the function and sends back a `function_result`.
There is no index to build or host: Gemini runs the search on the server. Developers can keep frequently used tools loaded up front and defer the rest. Tool Retrieval also works with prefix caching. Deferred schemas stay out of the prompt's opening section, and schemas loaded by the model are added later in the conversation, leaving the cached prefix unchanged between turns.

Enabling `tool_search` adds a small, fixed block of input tokens, and each schema the model loads is billed as input for the rest of the conversation, just like a tool declared up front. Token savings depend on whether the schemas left unloaded outweigh those retrieved; Google recommends measuring usage against each application's traffic.
Tool Retrieval works with Gemini 3.6 and later models, including all Gemini 4 models, in the Interactions API.

Google is previewing Tool Retrieval in its Interactions API for Gemini, giving developers a way to surface relevant tool descriptions when needed as agents work with larger sets of functions.
Tool schemas explain what a function does and which inputs it requires. Instead of including every tool’s full schema with each request, Tool Retrieval makes relevant schemas available as needed. Sending long lists of descriptions can increase input tokens and processing time, while making it harder for a model to choose the right tool.
The retrieval step also creates a limitation: if it misses a relevant tool, that tool may not be available for the model to select. The feature is in preview.
Google’s Gemini API includes built-in tools such as Google Search, File Search and Code Execution. Developers can also connect custom functions. Tool Retrieval is part of Google’s Interactions API, which supports multi-turn workflows and server-side state management and reached general availability in mid-2026.
