DGX Spark 2台でLLM生成1.8倍速、llama.cppがNCCLに対応
劉 尭
2026年11月9日 16:13
 　NVIDIAのAIミニPC「DGX Spark」を2台つなぐと、LLMの推論速度が1台の最大約1.8倍になる。ggml-orgは11月4日(米国時間)、ローカルLLM推論エンジン「llama.cpp v0.9.0」を公開した。このバージョンでは、内部で使用するテンソル演算ライブラリ「ggml」をv0.29.0に更新した。これにより、複数台のマシンでテンソル並列推論を行なう際の通信に、NVIDIAの通信ライブラリ「NCCL」を使用できるようになった。 
 　llama.cppはLLMの推論エンジン。GGUF形式のモデルを、CPUや各社のGPUを使ってローカルで実行できる。ggmlはその土台となるマシンラーニング向けのテンソル演算ライブラリだ。 
 　ggml v0.29.0では、別々のプロセスとして動作する複数のランク(並列処理に参加する各単位)の間で集団通信を行なうためのバックエンドインターフェイスを新たに追加した。CUDAバックエンドではこれをNCCLで実装しており、RPCサーバーはNCCLが利用可能な場合にこのインターフェイスを使用する。NCCLは、NVIDIAが提供するGPU間の集団通信ライブラリで、複数GPUの演算結果を集約するAllReduceなどの処理を担う。 
 　テンソル並列は、各層の演算を複数のGPUに分割して同時に処理する方式。llama.cppにはすでに、RPCサーバーを介して複数台のマシンでテンソル並列を行なう機能が取り込まれている。各マシンが計算した部分的な結果は、2台の間で直接データを交換する独自の方式で集約していた。今回の変更で、RDMAで接続したマシン間のこの集約処理に、NCCLを使用できるようになった。リリースノートでは「初期サポート」と位置付けられている。 
 　NCCL対応を実装した開発者は、DGX Sparkで「Qwen3.8-27B」の推論速度を測定。その結果、2台でNCCLを使用してテンソル並列を行なうと、プリフィルが1,348.29tok/s、デコード(生成)が23.51tok/sになったという。1台ではプリフィルが846.54tok/s、デコード(生成)が13.02tok/sだったため、それぞれ約1.6倍と約1.8倍に向上した。 
 　NCCLを使わない従来の方式でも、2台でのデコード速度は1台の約1.7倍まで伸びていた。一方、プリフィルは約1.1倍にとどまっていた。開発者は、デコードはプリフィルに比べて1回の集団通信でやり取りするデータが少ないため、NCCLの効果はプリフィルで大きく表われると説明している。 
 　このほかllama.cpp v0.9.0では、OCP FP8 E4M3形式の量子化への対応、マルチシーケンス推論時の統合KVキャッシュを効率化する操作「flash_attn_ext_rows」、汎用のバッチテンソルコピーAPIが追加された。また、新たなモデルへの対応なども行なわれた。

what's the reason why using NCCL is so much faster for PP vs TG? Maybe there is something to optimize in the generic path too
@am17an
,
Decode communicates far fewer tensor elements per collective than prefill. This explains why NCCL and pairwise have similar decode performance, while NCCL is significantly faster during prefill.
I tested three optimizations on the pairwise path:
Duplex exchange (
ggml-rpc.cpp
). Previously, rank 0 sent its entire payload before receiving, leaving one direction of the full-duplex link idle during each transfer phase. Changed 
comm_allreduce_pairwise
 to exchange chunks, with both ranks sending a chunk and then receiving, allowing traffic in both directions concurrently.
Deeper send queue (
transport.cpp
). Previously, 
rdma_send
 posted one 256 KiB work request and waited for completion before posting the next. Changed it to allow up to four outstanding sends, reducing gaps between transfers. Increasing the depth further to eight did not improve performance.
Direct registered buffers. Previously, the data path was 
GPU → application host buffer → RDMA host buffer → network
, with the reverse copies on receive. Replaced the intermediate buffers with persistent, pinned host buffers registered directly with RDMA: 
GPU → registered host buffer → network
. This eliminated the extra host-to-host copies while retaining GPU ↔ host transfers.
Further improvement likely requires restructuring the collective into an overlapping pipeline of GPU transfers, network communication, and reduction.

The 
comm_attach
 interface helps to get rid of 
ggml_backend_comm_init_rank_t
, but it introduces additional work to change the code for the one-process scenario. And it seems we still need a new interface for bootstrapping the initial information exchange between processes (ranks).
Another option is to keep two different sets of APIs for the one-process and multi-process scenarios. I'll replace the two new interfaces (
ggml_backend_comm_get_unique_id_t
, 
ggml_backend_comm_init_rank_t
) with more generic ones that can handle libraries like NCCL. For example:
typedef bool   (*ggml_backend_comm_bootstrap_callback)(void * user_data, const void * send_buf, void * recv_buf, size_t size);
typedef void * (*ggml_backend_comm_init_rank_t)(ggml_backend_t backend, int rank, int world_size, ggml_backend_comm_bootstrap_callback bootstrap_callback, void * bootstrap_callback_data);
The first one is implemented by the caller and moves the bytes between ranks. The library decides what to exchange and how many rounds to run, so different libraries can do their own initial information exchange. The second one is similar to the current 
ggml_backend_comm_init_rank_t
, with the new parameter 
ggml_backend_comm_bootstrap_callback
.
